## 1. 全景与状态机

### 1.1 生命周期

```
需求输入（Figma 链接 / 一句话 / wiki）
   │
   ▼
【预研】不建课题卡。AI：新板块先提取需求事实到 figma/，
        再粗粒度摸底（相关代码现状 / wiki 资料 / 第三方能力）
        → BOARD 预研区登记一行（防会话中断丢失）
   ▼
【对话】AI 报告：需求理解 + 课题拆分建议 + 疑问清单
        人：纠正理解 / 回答疑问 / 补充约束；多轮直至收敛
   │ ────── G1 人确认拆分边界（对话收敛即确认）──────
   ▼
【建卡上板】建课题目录：课题卡.md（课题卡，目标/范围来自对话收敛结论）
            + research/_log.md 首条（预研发现回填）；直接以 researching 起步
            多功能点 / 跨课题拆分 / 有需求澄清时，同时创建 需求分析.md，以 FR-n 建需求基线
   ▼
【看板】BOARD.md 课题表：一行一课题，唯一进度入口
   ▼
【调研】围绕范围内 FR-n 形成三类产出（可多轮，顺序不必固定）：
        ① 需求理解：功能规则、边界、交互约束（对齐 figma/ 事实与代码现状）
        ② 选型：存储/接口/协议/第三方能力的方案对比与推荐
        ③ 设计评审：对已有设计或研究稿的评审意见与风险清单
        过程进 research/_log.md，长结论进 research/ 一研究一文件（NN-slug.md）
        产品事实待确认 → 需求分析 Q-n；技术事实待查 → 课题卡 U-n；
        需人定方向 / 边界 / 风险 → 课题卡 D-n → 课题转 review
   │ ────── G2 人逐条确认 Q-n、裁决 D-n（可多轮回退）──────
   ▼
【结论定稿】人说「定稿」→ settled；阻塞 Q/U 清零，D 全部闭环，FR 均有明确去向
        调研型课题（结论一句话 / 拆分类）：课题段到此为止
        方案型课题（需产出技术方案上会）▼
【方案起草】proposing：AI 以 settled 结论 + research/ 研究文件起草 设计文档.md
        （结构对齐设计文档模板/02，按规模裁剪），开头附评审要点页；完成转 proposed
   │ ────── G3 团队评审（人组织，意见按三粒度回流，可多轮）──────
   ▼
【评审通过】人说「评审通过」→ approved，课题段终点；设计文档.md 冻结，
        立项后即开发段 02-设计文档 的基础。settled / approved 均可由人重开（§4.4）
```

**为什么建卡前先对话**：课题卡的目标/范围若由 AI 单方面起草，是拍脑袋；经过预研和对话收敛后建卡，卡的质量高，BOARD 上不出现一堆空卡。预研的中间过程不落盘（留在会话/subagent 上下文），收敛结论在建卡时写入 课题卡.md 与 research/_log.md 首条。

两段式职责：

| 段   | 位置                          | 回答的问题                           |
| --- | --------------------------- | ------------------------------- |
| 课题段 | `docs/topics/`              | 要不要做、做成什么样、技术方案选什么、方案文档能否通过团队评审 |
| 开发段 | 由人届时决定（features/ 流水线现有约定不变） | 怎么实现、怎么交付                       |

### 1.2 状态机与 Gate

- 状态机：`researching → review → settled`；方案型课题续 `proposing → proposed → approved`；任意态可 `paused`；draft 态已取消（预研对话承担其职责）
- 课题两类（课题卡.md frontmatter `type`）：`research` 调研型——settled 即课题段终点；`design` 方案型——settled 后继续起草方案上会。建卡时由 G1 对话收敛判定，定稿时人可改口
- 术语注意：课题态 `review` 是 **G2 单人裁决**；「团队评审」是 **G3**（对 设计文档.md），两个动作不要混用

| gate    | 谁触发   | 内容                                                   |
| ------- | ----- | ---------------------------------------------------- |
| G1 拆分确认 | 人     | 预研对话收敛即确认，AI 随即建卡，并按创建规则建立 FR 需求基线                         |
| G2 结论裁决 | 人     | 确认阻塞 Q、逐条裁决 D；AI 完成关联位置回写，Q/U 清零且 D 全闭环后报告结论，人说「定稿」→ settled |
| G3 团队评审 | 人（组织） | 团队对 设计文档.md 评审；意见按 §4.3 三粒度回流，可多轮；人说「评审通过」→ approved |
| 立项开发    | 人     | approved 之后是否立项、如何进入开发流程，**届时时由人决定，机制不预设**           |

### 1.3 AI 会话动线

```
开场：读 BOARD.md → 定位课题与卡点 → 读课题 课题卡.md（+ 需求分析 FR 清单 + research/_log.md 尾部）
      （ BOARD 预研区有未收敧行 → 恢复预研对话，见 §3.1 ）
调研：按资料清单派 subagent（微服务代码 / wiki 经 mcp-atlassian / 第三方文档）→ 结论写 research/（长结论建研究文件，过程进 _log.md）
      需求规则更新进 需求分析.md（FR/Q），技术未决进 课题卡 U，需人定的事项起草 D
裁决：D-n 转入 课题卡「待人裁决」→ 课题转 review → 向人报 Q/D 清单 → 人裁决后同轮回写闭环（§4.3）
方案：settled（方案型）→ 人说「起草方案」→ 设计文档.md（FR 映射到章节）→ proposed → 人组织团队评审（G3）
收尾：同步课题 课题卡.md + BOARD.md（开发段产物含发布事项时，同步 docs/发布.md）
```

各阶段「人说的话 / AI 行为」逐段见 §3。

## 2. 文件体系

```
├── topics/                # 课题目录：需求理解 / 选型 / 设计评审（非开发）
│   ├── _template/         #   建卡模板（课题卡 / research/_log）；需求分析模板在 设计文档模板/01
│   └── NNNN-slug/

└── features/              # 开发期流水线产物（课题段不涉及，衔接方式届时由人决定）
```

### 2.2 文件职责（唯一事实源）

| 文件 | 何时存在 | 唯一职责 | 写法约束 |
| --- | --- | --- | --- |
| `figma/`（全局） | 新板块预研时提取 | 原始需求事实：原型中的功能、文案、规则，可被多课题引用 | 文件头记提取日期与变更行；只存链接+摘要，不整页粘贴 |
| `BOARD.md`（全局） | 常设 | 唯一进度入口：一行一课题 + 预研区 | 看板是视图非事实源，以课题卡为准；行长度纪律见 §2.6 |
| `发布.md`（全局） | 常设 | 发布事务清单：DDL / 后台配置 / 开关 / 顺序 / 回滚，按批次组织 | submit 收口时汇总进来；单课题不单建发布文档 |
| `课题卡.md` | 建卡 | 课题控制面：目标、范围、需求基线指针、资料清单、D 决策、结论、U 技术未决、Gate | frontmatter `status` 是课题状态事实源；规则正文不在此重复 |
| `需求分析.md` | 多功能点 / 跨课题拆分 / 有需求澄清 / 需追踪到研究或设计时 | 需求基线：FR 功能点、业务规则、边界、用户可观察结果、Q 需求澄清 | 引用 figma/ 事实不复制；不放技术方案和 D 的重复结论 |
| `research/_log.md` | 建卡 | 过程审计：每轮动作、发现、建议和未决，以及 FR/Q/U/D 关联 | **append-only，禁止改写历史条目** |
| `research/NN-slug.md` | 形成长技术结论时 | 技术证据：方案对比、接口建议、链路分析、评审意见 | 开头标明关联 FR/D 和结论去向；可修订，须在 _log.md 追记 |
| `设计文档.md` | 方案型课题 proposing 起（§3.6） | settled 结论形成的技术方案，团队评审对象 | 每个范围内 FR 映射到设计章节；approved 后冻结 |
| `test/`（课题内） | 可选：需要端到端 / 集成验证时 | 课题验证脚本与报文，README 即操作说明 | 有些课题不需要测试，不强制建；**单元测试归代码仓**随代码提交 |
| `features/NNNN/`（开发段） | 人声明进入开发后 | Request / RequireSpec / design / submit 流水线产物 | RequireSpec 是课题需求分析的 FR 映射，不另立需求基线；自测规范与测试交付见 设计文档模板/03、04 |

- 课题卡 目标与范围来自 G1 对话收敛结论，AI 不再单方面起草。
- 课题卡 只列需求分析链接和范围内 FR，不复制功能规则；需求分析只引用 D-ID，不复制决策当前结论——两份文件是「内容基线 + 控制面」，不是两份需求文档。
- 单一简单需求可不建需求分析，由 课题卡 目标直接覆盖；一旦需要拆成功能点、澄清或追踪去向，立即按 `设计文档模板/01-需求分析.md` 补建。
- 资料清单（课题卡内）：Figma 链接、wiki pageId、代码路径、第三方 URL + 消化状态（`未读 → 已读 → 已核`，已核 = 与代码交叉验证）。
- 调研只记发现与建议，中间推理留在 subagent 上下文；一句话能说清的结论可直接写 课题卡.md，research/ 可只有 _log.md。
- 测试归属：单元测试写在微服务仓 Go test 随代码提交；端到端 / 集成验证脚本放课题 `test/`；测试交付说明用 `设计文档模板/04-测试交付.md`（开发段）。
- 发布归口：设计与交付中产生的发布事务（DDL / 后台配置 / 开关 / 顺序 / 回滚）在 submit 收口时汇总进 `docs/发布.md` 对应批次，单课题不单建发布文档；登记口径见 `设计文档模板/05-发布规范.md`。
- topics 的 需求分析.md 是课题段需求基线。进入开发段时，它作为 RequireSpec / design 的输入，不另起一份相互独立的当前状态。

### 2.3 引用方向

`figma/ → 需求分析（FR/Q）→ research（证据）→ 课题卡（D/结论/Gate）→ 设计文档 → features（RequireSpec 映射 / design / submit 勾对）→ 发布.md`

允许双向链接；**禁止在下游复制另一份「当前状态」**，下游只引用 ID 与链接。

### 2.4 FR 功能点追踪

- 每个功能点使用课题内稳定的 `FR-n`；编号不复用，跨课题引用写 `NNNN/FR-n`。
- FR 状态只表示需求清晰度，不表示开发进度：`待分析 / 待确认 / 待裁决 / 已明确 / 已移出 / 不做`。
- `待确认` 必须关联 Q-ID；`待裁决` 必须关联 D-ID；`已移出 / 不做` 必须写明依据和去向。
- research 文件和 _log 条目引用受影响的 FR/D；design 型课题在 proposed 前把每个范围内 FR 映射到设计章节。
- research 型课题 settled 前，每个范围内 FR 必须有研究结论、拆分归属或不做依据；design 型课题 settled 前必须有明确结论去向。
- 端到端口径：03-自测规范 / 04-测试交付 的「对应需求点」、submit 的「功能点勾对验收」一律使用 FR-n（跨课题写 `NNNN/FR-n`），使 FR 从需求、设计、测试到交付、发布全程可追。

### 2.5 设计文档的独立可读性

设计文档可能被单独上传 Wiki 或转发，必须脱离课题的 课题卡、需求分析和 research 上下文独立可读：

- 正文以通俗、明确的名称为主；领域缩写首次出现时写出全称或中文含义，后续可以使用简称。
- `FR`、`D`、`E` 等内部编号只用于追踪，不得代替具体含义；出现时同时写明功能、决策或发现的名称，例如「FR-3：事件历史」「E13：Rain Sensor 跳过统计口径」。
- `Q`、`U` 等调研过程编号原则上不进入最终设计文档；确需引用时同时写明问题主题和已确认结论。
- FR 覆盖映射必须同时包含编号、功能名称和设计章节。
- 文内章节引用必须使用 Markdown 链接，例如 `[historage 侧：写入](#historage-侧写入)`；不使用 `§写入` 等不可点击且依赖读者猜测的简称。
- 术语较多时可在文档前部增加「术语与编号」表，但该表只能集中索引，不能替代正文首次解释。
- 相对链接只用于提供来源和证据，不承担关键概念、边界或结论的解释。

存量处置（已完成 08-21）：`docs/research/` 3 篇已迁入对应课题 research/（`virtual-zone-storage-and-api.md` → 0001；`ai-watering-plan-design.md`、`ai-agent-architecture.md` → 0003），全局 `docs/research/` 已删除。现有课题不因版本升级批量重写，后续继续调研或进入下一 Gate 前按新模板增量补齐。

### 2.6 看板（BOARD.md）

```markdown
|---|---|---|
| 通知需求（无 Figma，待产品澄清） | 对话中 | 08-21 |

## 课题表
| ID | 课题 | 状态 | 服务 | 下一步 / 卡点 | 更新 |
|---|---|---|---|---|---|
| [0002](topics/_archive/0002-events-history/课题卡.md) | 事件 History 与 rain-skip | researching | historage, device | 调研 wiki 三篇 + 写入路径 | 08-20 |
```

- 行长度纪律：「下一步 / 卡点」≤ 2 个短句 + 链接。交付细节写 features submit.md，发布事项写 发布.md，实现要点写课题 设计文档 / research——都不在看板展开。

## 3. 阶段流程

> 每阶段一段：上半是**人说的话**（触发该阶段，提示词可原样复制，`〈〉`内按需替换），下半是 **AI 的行为约定**（收到后做什么）。

### 3.1 预研与对话（G1）

**人说**：

```
预研这个需求：〈Figma 链接 / 一句话需求 / wiki 链接〉
```

**AI 行为**：

1. 新 Figma 板块 → 提取需求事实到 `figma/`（get_metadata 结构树 + 脚本过滤，不用截图）；文件头记提取日期，再提取同一板块时登记变更行——发现已建课题的既有 FR 受影响，走课题重开或新 D（§4.4）
2. 粗粒度摸底：相关微服务代码现状、wiki 资料、第三方能力——够判断拆分即可，不做深研（subagent，中间过程不落盘）
3. 若对话跨会话，BOARD 预研区登记一行
4. 报告三件事：**需求理解**（我理解的产品要什么）/ **拆分建议**（建几个课题、各自目标一句话）/ **疑问清单**（阻塞拆分的问题）——人来对话收敛：纠正理解 / 回答疑问 / 补充约束
5. 人在对话中说「建卡」或确认拆分 → 视为 G1 通过，进入 3.2

**拆分原则**：

- 一课题 = 一句话目标 + 一份独立成立的结论；**不按 Figma 页面拆，不按微服务拆**
- 跨服务课题不拆（如 VZ 存储），`services` 字段标多值，调研分别派 subagent 读对应微服务
- 大板块（如 Device Settings）先建**伞形课题**只做拆分，子课题各自建目录——子课题用**全局顺延编号**（0006、0007…），不嵌套编号；子课题全部建卡后伞形课题转 settled，结论即拆分清单
- 明确的小需求可**跳过课题段直接走流水线**——跳过由**人声明**，AI 不自行判断；课题只服务于需要调研的需求

### 3.2 建卡上板（G1 通过后，AI 一次做完）

**人说**：

```
建卡：课题按刚才收敛的拆分来
```

**AI 行为**：

1. 从 `_template/` 建课题目录（下一个可用编号）
2. 课题卡.md：目标/范围写对话收敛结论（课题卡以 **researching 起步**，draft 态已被预研对话取代）；资料清单填预研摸到的资料 + 消化状态；可继续调研的技术疑问写入 `U-n`；status=researching
3. 满足创建条件（多功能点 / 跨课题拆分 / 需求澄清 / 需追踪到研究或设计）时同时建 `需求分析.md`，登记 FR 与产品事实疑问 `Q-n`
4. 需人定方向、边界或接受风险的事项写为 课题卡 `D-n`
5. research/_log.md 首条（标注「预研回填」）：预研动作、发现、遗留的 Q/U/D
6. BOARD 预研区该行移入课题表
7. 向人复述课题卡要点（目标/范围/FR 清单/未决），确认无偏差后开始 3.3

### 3.3 调研（researching，可多轮）

**人说**（开场或指派）：

```
继续调研 〈课题 ID 或名称〉：〈本轮要消化的资料 / 要回答的问题〉
```

**AI 行为**：

1. 读课题 课题卡.md + 需求分析 FR 清单 + research/_log.md 尾部，明确本轮目标
2. 按资料清单派 subagent（微服务代码 / wiki 经 mcp-atlassian / 第三方文档），只带结论回主会话
3. research/_log.md 追加一条：日期 + 动作 + 发现 + 建议 + 未决（关联 FR/Q/U/D ID）
4. 资料消化状态推进（未读 → 已读 → 已核）
5. 长技术结论（方案对比 / 接口设计建议 / 评审意见）在 research/ 下建研究文件（NN-slug.md），开头标注影响的 FR/D 与结论去向；课题卡.md 结论小节链接。需求规则更新走 需求分析.md 的 FR 与 Q，不写进研究文件
6. 问题分流：产品事实待确认 → Q-n（并同步 FR 状态为待确认）；技术事实待查 → U-n；需人定方向 / 边界 / 风险 → 起草 D-n（四要素 + 关联 FR）→ 课题转 review → 进入 3.4

### 3.4 裁决与回写（review ⇄ researching 循环，G2）

**AI 主动报告**（课题进入 review 时）：

```
课题 0002 转入 review，待你处理：
- 待确认 Q：Q-1 〈问题〉
- 待裁决 D：D-1 〈背景+问题+建议+影响，关联 FR-n〉
- 待回写 D：D-2 已裁决（结论…），回写还差 research/02
可整体回复，如「Q-1 是…；D-1 同意；D-2 已回写完毕」
```

**人说**（三种粒度，可混用，协议见 §4.3）：

```
裁决 0002：Q-1 是…；D-1 同意；D-2 选 B，理由是…；D-3 暂缓   ← 逐条
纠偏：方向错了，应该从 X 入手                        ← 纠偏回退
补充约束：必须兼容 MSC08 现网固件                    ← 记入课题约束
```

**AI 行为**：

- 逐条确认 / 裁决 → 按 §4.3 同轮完成回写闭环：Q 写结论；D 保留原建议、追加 ✅ 结论、更新关联 FR/research/结论，_log 追记；暂缓项保留原位
- 纠偏 → research/_log.md 追加纠偏记录，课题回退 researching 按新方向调研（已闭环条目不动；需推翻时新建 D-ID）
- 补充约束 → 记入 课题卡.md 范围或需求分析跨功能约束，后续建议显式引用
- **Q/U 清零、D 全闭环且结论完整 → AI 只报告结论要点，课题停在 review**；人说「定稿」才转 settled（终态由人宣布，AI 不越 gate）
- 未清零 → 继续循环

### 3.5 定稿（review → settled，人的动作）

**人说**：

```
0002 定稿
```

**AI 行为**：定稿前置检查——范围内 FR 均为已明确 / 已移出 / 不做且有去向（未建需求分析时确认目标覆盖单一需求）、阻塞 Q 与 U 清零、D 无待裁决 / 待回写 / 暂缓；通过后 课题卡.md 结论小节定稿（链接 research/ 研究文件），BOARD 该行状态置 settled。

- 调研型课题（type=research）：课题段到此为止；是否立项进入开发由人届时另行决定
- 方案型课题（type=design）：settled 后下一动作是起草方案，AI 报告「课题已 settled，可起草方案，说『起草方案 0003』开始」（§3.6）

### 3.6 方案起草与团队评审（方案型课题：settled → approved，G3）

**人说**（发起起草）：

```
起草方案 0003
```

**AI 行为**（proposing，AI 自主推进，无 gate）：

1. 以 settled 结论 + research/ 研究文件为素材起草 `设计文档.md`，**不引入新结论**——评审中发现的新问题走待人裁决，不直接改方案
2. 结构对齐 `设计文档模板/02-设计文档.md` 骨架，按其裁剪规则按规模裁剪（小=单文件精简 / 中=标准 / 大=多文件拆章）；每个范围内 FR 映射到设计章节
3. 文档开头加**评审要点页**：方案一句话、关键决策点（来自已闭环 D-ID）、风险清单、希望评审重点讨论的问题——团队成员 5 分钟读完即可上会
4. 起草完成前检查独立可读性（§2.5）：缩写首次出现已解释；正文不存在无名称的 FR/D/E 等内部编号；章节引用均为可点击的 Markdown 链接；读者不打开课题其他文件也能理解方案
5. 完成后课题转 **proposed**，AI 报告：文档位置 + 评审要点页内容，提示人安排评审

**G3 团队评审**（proposed，人组织）：

- 评审由**人组织**（约会议 / 发文档），AI 不参与组织；会议记录由人带回对话
- 意见回流按 **§4.3 三粒度**处理：
  - 逐条（同意 / 修改意见）→ AI 修订 设计文档.md 对应章节，research/_log.md 追记评审轮次、修订摘要与关联 FR/D ID
  - 纠偏（评审否决选型）→ 人说「重开」（§4.4），课题回 researching；推翻的具体 D-ID 由新一轮裁决处理
  - 补充约束 → 记入 课题卡.md，设计文档.md 修订时显式引用
- 每轮修订 设计文档.md 头部记一行版本（日期 + 轮次 + 一句话变更）

**人说**（评审通过）：

```
0003 评审通过
```

**AI 行为**：设计文档.md 冻结（头部标注评审日期与结论），课题转 **approved**，课题段终点。立项后 设计文档.md 即开发段 02-设计文档 的基础，衔接方式届时时由人决定。

## 4. AI-人协同协议

**角色分工**：AI 消化资料、起草问题与建议、执行回写；人确认产品事实、定方向、裁决和纠偏。

### 4.1 Q / U / D 分流

| ID | 什么问题 | 唯一落点 | 谁推进 |
| --- | --- | --- | --- |
| Q-n | 产品事实或业务规则是什么 | 需求分析「需求澄清」 | 产品 / 人确认；确认后保留原问题和结论 |
| U-n | 技术事实尚未查清 | 课题卡「待调研」 | AI 继续调研；查清后写 research 或 课题卡 结论 |
| D-n | 需要选择方向、划分职责边界或接受风险 | 课题卡「待人裁决」 | AI 起草，人裁决，AI 回写闭环 |

问题性质变化时不复制当前结论：例如 Q-2 发现实为职责取舍，就把 Q-2 标为“转 D-3”，后续状态只在 D-3 维护。

### 4.2 待人裁决格式（D-n）

每项 D-ID 必须自包含，并关联受影响的 FR：

```markdown
### D-1 · rain-skip 事件枚举 · 待裁决
- 关联功能：FR-3
- 提出日期：2026-08-25
- 背景：事件 type 现有 1-3，原型要求 rain-skip
- 问题：新增 type=4，还是复用 sensor-skip 加子类型？
- 建议：新增 type=4。理由：协议可读、App 分支简单；风险：旧 App 对未知 type 的行为未验证
- 影响：上报协议、historage 存储、查询接口
- 裁决：待裁决
- 回写：需求分析 FR-3；research/02-event-model.md；设计文档 §4
```

状态流转：`待裁决 → 已裁决待回写 → 已闭环`。人要求暂缓时标 `暂缓`，仍阻塞收口；旧决策被推翻时标 `已替代（见 D-n）`，新建 D-ID 承载新一轮裁决。

### 4.3 人的回复与 AI 回写

人的回复按三种粒度处理：

| 粒度 | 人怎么说 | AI 做什么 |
| --- | --- | --- |
| 逐条确认 / 裁决 | 「Q-1 是…；D-1 同意；D-2 选 B，理由…；D-3 暂缓」 | Q 写结论；D 保留原建议并追加 `✅ 已裁决：结论（日期，裁决方）`；暂缓项保留原位 |
| 纠偏 | 「方向错了，应该从 X 入手」 | _log 追加纠偏记录；课题回 researching；需推翻旧 D 时新建 D-ID，旧项标已替代 |
| 补充约束 | 「必须兼容 MSC08 现网固件」 | 更新需求分析跨功能约束或 课题卡 范围；受影响研究和设计显式引用 |

D-ID 获得裁决后，AI 在同一轮完成以下闭环：

1. 状态先改为 `已裁决待回写`，保留背景、问题、建议和影响。
2. 更新关联 FR 的规则、状态和 Q；不在需求分析复制一份决策正文。
3. 更新受影响的 research 结论、课题卡 结论、设计文档或下游课题；需要时同步 BOARD 下一步 / 卡点。
4. research/_log.md 追加裁决与回写摘要，列出 FR/Q/U/D ID。
5. 所有回写完成后才改为 `已闭环`；任何回写未完成都不得把课题转 settled。

三粒度协议也适用于 G3 团队评审意见回流（见 §3.6）。裁决记录不删原文，结论修订不静默改；AI 收尾时若课题处于 review，按 D-ID 报告待裁决 / 待回写 / 暂缓清单，便于一次批量回复。

### 4.4 重开（settled / approved → researching）

终态非坟墓。团队评审否决选型、新证据推翻结论、原型变更影响既有 FR 时，**人**说「重开 0002，原因…」；AI 在 _log.md 追加重开原因，课题回 researching。旧 D-ID 保留并标明是否被新 D-ID 替代。

## 5. 硬规则（AI 必须遵守）

1. **Gate 只由人推进**：G1/G2/G3 与「定稿」「评审通过」均为人触发；Q/U 清零且 D 闭环后 AI 只报告结论，课题停在 review 等人定稿，不得自行转 settled（§1.2、§3.5）
2. research/_log.md 只追加，不改写历史条目；研究文件与需求分析的修订须在 _log.md 追记说明（§2.2）
3. 待人裁决 D-n 由 AI 起草且自包含（背景+问题+建议+影响+关联 FR）；人裁决后保留原建议并追加 ✅ 结论，回写全部完成才标已闭环（§4.2/4.3）
4. FR 编号课题内稳定不复用；裁决 / 需求变更必须同步更新关联 FR、Q/U/D、research 结论与 BOARD，不得只改一处（§2.4）
5. 每次会话收尾：更新所动课题 课题卡.md（updated + status）+ 同步 BOARD；新建课题必须同时上板；预研对话跨会话时在 BOARD 预研区登记（§2.6、§1.3）
6. 调研 subagent 只把结论带回主会话，中间过程不落盘（§3.3）
7. 开场以 BOARD 为入口，发现看板与课题卡不一致，以课题卡为准并在收尾纠正（§1.3）
8. 设计文档.md 起草不得引入 settled 结论之外的新决策；评审中的分歧走待人裁决或重开，不静默改方案（§3.6）
9. 发布事务（DDL / 后台配置 / 开关 / 顺序 / 回滚）在 submit 收口时汇总进 `docs/发布.md` 对应批次，不在课题内另建发布文档（§2.2）
